# مشكلات Tdrive API المطلوب حلها

## عائق الحذف الحالي: جلسات pending ذات expiresAt منقضٍ

في `2026-11-10T08:31:52Z` فُحص مجلد المستخدم «تمرين» قراءة فقط: صفر ملفات وصفر مجلدات فرعية، لكن `GET /uploads?path=/Obsidian/X0/تمرين/&active=1` أعاد جلستين:

| المعرّف | الحالة | active/cancellable | createdAt | expiresAt |
|---|---|---|---|---|
| `72e7b121-f4e0-462e-8a4b-4bb7f5be549b` | pending | true/true | 2026-11-06T15:26:51.762Z | 2026-11-07T15:26:51.762Z |
| `2ae0488e-cfa1-4a47-9c1b-4e93d20c584d` | pending | true/true | 2026-11-08T06:36:35.148Z | 2026-11-09T06:36:35.148Z |

هذا مختلف عن API-001 الخاص بجلسات committed الذي أصلح: العائق الآن جلسات pending قديمة يعرض لها الخادم تاريخ انتهاء مضى وما زال يعدّها نشطة. آخر رفض محفوظ للمجلد كان `UPLOAD_IN_PROGRESS`، request id `49ae18fe-f1a1-4c42-b511-02e16d722536`.

**المطلوب من API:** توضيح معنى expiresAt وتصحيح سياسة انتهاء الجلسات وحالتها الفعلية وفحص الحجب. إن كان انتهاء صلاحية الرفع يعني أنه لم يعد قابلًا للنشر، يجب تمثيل الحالة بوضوح وعدم عرضه كرفع جارٍ يمكنه النشر، مع إبقاء بيانات الاستعادة إذا كانت السياسة تتطلب ذلك. إن كان تنظيف البيانات مؤجلًا، أعيدوا حالة وسببًا يصفان ذلك بدل طلب finish/abort لجلسة انتهى وقتها. يجب اختبار التوافق بين القائمة والحالة ومسار حذف المجلد واستئناف جلسة منتهية، ومنع نشر متأخر تحت tombstone.

**قرار المستخدم:** اختار إبقاء الجلستين وبياناتهما. لم تلغهما أدوات الفحص، ولم يُنفذ حذف للمجلد لإخفاء العائق. لا تفترضوا إذنًا بمسح البيانات غير الملتزمة عند إصلاح سياسة expiry؛ وضحوا الاستعادة والتنظيف والاحتفاظ أولًا.

فُحص العقد الجديد بطلبات حية على بيانات مولدة ومعزولة عند `2026-11-10T06:46:52Z`، وانتهى بتنظيف مجلد الاختبار وإطلاق القفل دون المساس بملاحظات المستخدم:

| API-002 | أصبح ifEmpty موثقًا ومتاحًا | حذف مجلد يحوي ملفًا رفض بـ409 FOLDER_NOT_EMPTY دون حذف الملف؛ `73542bb7-11a9-482b-889a-df3c9b4f635f` |
| API-003 | أصبح sync/leases موثقًا ومتاحًا | الاستحواذ والتجديد والإطلاق نجحت؛ صاحب آخر والكتابة بلا رمز أو برمز سابق رفضت بـ423 LEASE_CONFLICT |

نقاط مهمة للعقد الحالي:

- `contentVersion`/`content_version` جيل المحتوى الحالي. `version` في إيصال revision هو ترتيب النسخة السابقة المؤرشفة، وليس الجيل الحالي؛ ظهر إيصال contentVersion=3 وversion=2.
- تغيير name/path/favorite يتم معًا في PATCH ذري ولا يغير contentVersion؛ لا تخلط metadata مع content في الطلب نفسه.
- TTL للقفل 15–300 ثانية. التجديد يعيد expiry/serverTime لكنه لا يعيد الرمز السري؛ احتفظ بالرمز الحالي في الذاكرة فقط.
- الكتابة المحمية تستعمل X-Sync-Path وX-Sync-Lease. القفل خاص بسطح API؛ UI/WebDAV خارج عقد القفل، لذا تبقى شروط إصدار المحتوى ضرورية.
- lost acquisition response لا يستعاد بوسم owner؛ انتظر انتهاء TTL بدل تكرار استحواذ مجهول النتيجة.
- legacy receipt قد يحمل contentVersion=null؛ لا تخترع له جيل الرأس الأحدث.

**توسعة لا تزال مطلوبة إن أردتم ضمان الاسترجاع أيضًا:** في `2026-11-10T07:53:24Z` جُرب POST `/files/:id/versions/:versionId/restore` مع expectedVersion=1 والجيل الحالي 3؛ قُبل برد 200، request id `1003e99f-1159-4ff1-b38c-86d140828f17`. العقد الحالي لا يعد بإنفاذ هذا الشرط في restore، لذلك لا يصنف ذلك كخرق لعقد PATCH/uploads المصحح، لكنه يترك الاسترجاع دون precondition موثقة ضد UI/WebDAV. المطلوب توثيق ودعم شرط الجيل الحالي على restore، واختبار رفض stale generation دون تغيير الرأس. القفل وحده يحمي كتابات API، لا تلك الأسطح الأخرى.

الاختبار أكد النتائج الموضحة، لكنه ليس تدقيقًا لمصدر الخادم أو إثباتًا لكل ترتيب تزامن ممكن. البنود التالية أرشيف للفحص السابق في 2026-11-09.

تاريخ التقرير: 2026-11-09.

هذا المستند موجه لمطور الخادم. يعتمد على الاختبارات الحية المسجلة أثناء فحص Tdrive Sync، وليس على نجاح الاختبارات الاصطناعية وحدها. لا يحتوي مفاتيح API أو محتوى ملاحظات المستخدم.

**نطاق الأدلة:** تأكد خلل واحد بإعادة إنتاجه على الخادم الحقيقي. بقية البنود متطلبات لعقد API آمن ومتزامن، وليست أعطالًا حية مثبتة. لم يكن مصدر الخادم أو مخطط قاعدة بياناته متاحًا للفحص؛ لذلك تفاصيل موضع التصحيح أدناه توصيات، لا وصفًا لاستعلام تمت قراءته.

## API-001: المجلد الفارغ يبقى محجوبًا بعد revision مكتمل

### السلوك المؤكد

بعد نجاح تحديث محتوى ملف عبر جلسة revision، تصبح الجلسة `committed` والملف `ready`. مع ذلك، يرفض الخادم حذف المجلد الذي احتوى الجلسة:

```http
DELETE /api/v1/folders?path=/Obsidian/X0/&name=<diagnostic-folder>
Authorization: Bearer <API_TOKEN>
```

الرد الفعلي:

```json
{
  "ok": false,
  "error": {
    "code": "UPLOAD_IN_PROGRESS",
    "message": "Finish or abort descendant uploads before trashing this folder."
  }
}
```

HTTP status: `409`.

يستمر الرفض حتى بعد نقل جميع الملفات إلى السلة، عندما تعيد قائمتا `/files` و`/folders` صفر عناصر داخل المجلد. محاولة إلغاء الجلسة المكتملة ترفض أيضًا بـ`409 FILE_STATE_CONFLICT`؛ أي إن الإجراء الذي تقترحه رسالة الحذف غير قابل للتنفيذ لهذه الجلسة.

### الأثر

- تعذر إكمال حذف المجلدات ومزامنة حذفها بين الأجهزة.
- بقاء مسارات قديمة فارغة بعد نقل الملفات أو إعادة تنظيمها.
- إعادة محاولات غير مفيدة ورسائل فشل متكررة.
- لا يمكن للإضافة إصلاح ذلك بأمان بإلغاء جلسة مكتملة أو حذف بيانات نهائيًا.

ظهر رمز الرفض نفسه في سجل المستخدم عند حذف مجلد «تمرين» لعدة ساعات. الخلل أعيد إنتاجه بصورة مستقلة داخل مجلدات تشخيص مولدة، دون الاعتماد على ملفات المستخدم.

### خطوات إعادة الإنتاج

1. أنشئ مجلد اختبار فريدًا، لا مجلدًا يحوي بيانات حقيقية.
2. ارفع ملفًا إلى المجلد وتأكد من أنه `ready`.
3. افتح جلسة تحديث عبر `POST /api/v1/uploads` باستخدام `baseId` و`mode: "replace"`.
4. ارفع الأجزاء وأنهِ الجلسة عبر `POST /api/v1/uploads/:id/complete`.
5. تحقق من أن `GET /api/v1/uploads/:id` يعيد `status: "committed"` و`revision: true`، وأن المحتوى الجديد قابل للتنزيل ومتطابق.
6. حاول حذف المجلد. النتيجة الملاحظة: `409 UPLOAD_IN_PROGRESS`.
7. انقل جميع ملفات الاختبار إلى السلة، وتحقق من فراغ المجلد بقائمتي الملفات والمجلدات، ثم أعد DELETE. الرفض يبقى.

**الاختبار الضابط:** إنشاء المجلد ورفع الملفات وتنزيلها دون إجراء revision سمح بحذف المجلد بنجاح في `2026-11-08T11:14:32Z`.

لإعادة الاختبار من مشروع الإضافة:

```text
node scripts/check-sync-live.js --cdc-probe
```

هذا الأمر ينشئ بيانات اختبار معزولة داخل مجلد مخفي فريد باستخدام إعدادات الحساب المحلية. قد يتعذر تنظيف المجلد بسبب العيب نفسه؛ لا تستخدمه على مجلدات حقيقية، ولا تشارك ملف الإعدادات أو المفتاح.

### التصحيح المطلوب

السلوك يشير إلى أن فحص وجود رفع جارٍ لا يميز الحالة النهائية للـrevision عن الرفع النشط. يجب مراجعة شرط الحجب في DELETE للمجلد وجميع الاستعلامات التي تجمع الجلسات التابعة لمساره.

- حدد الحالات النشطة صراحة من آلة حالات الخادم، بدل اعتبار كل حالة غير `ready` نشطة.
- اعتبر `committed` حالة نهائية للـrevision، مثلما تعد `ready` حالة نهائية للرفع الجديد.
- لا تصنف نسخ المحتوى المؤرشفة أو مراجع الجلسات المكتملة كرفع جارٍ.
- افصل مراجع تاريخ الإصدارات عن الجلسات النشطة، حتى إن بقيت السجلات النهائية محفوظة للتشخيص أو idempotency.
- نفذ تغيير الحالة وتحديث عداد/فهرس الجلسات النشطة بصورة متسقة مع إتمام العملية.
- راجع تنظيف الفهارس والمراجع عند نقل الملف أو حذفه إلى السلة؛ لا يجب أن يبقي مرجع نهائي مسارًا قديمًا محجوبًا.
- أبقِ حماية الحذف للجلسات النشطة فعلًا. لا تعطل `UPLOAD_IN_PROGRESS` بصورة عامة.

مثال على منطق غير كافٍ **للتوضيح فقط، وليس استعلامًا ثبت وجوده في المصدر**:

```text
any descendant upload where status != "ready"
```

هذا يحجب أيضًا revision حالته `committed`. البديل هو اختبار حالة نشطة موثقة، مع التمييز بين نوع السجل وحالته النهائية.

### اختبارات قبول التصحيح

- حذف مجلد يحتوي ملفًا `ready` وجلسة revision نهائية `committed` ينجح وينقل محتوياته إلى السلة حسب عقد الحذف.
- حذف المجلد بعد نقل جميع ملفاته إلى السلة ينجح، دون انتظار تنظيف سجل جلسة مكتملة.
- نقل ملف ذي revisions مكتملة إلى مسار جديد لا يبقي المسار القديم محجوبًا بسبب مراجع نهائية.
- حذف مجلد أثناء رفع نشط حقيقي يبقى مرفوضًا، دون فقد بيانات الجلسة.
- إلغاء revision مكتمل لا يصبح حلًا مطلوبًا لحذف المجلد؛ يبقى غير مسموح أو له سلوك نهائي موثق وآمن.
- تكرار السيناريو مع عدة revisions وملفات فارغة وCDC ورفع ثابت يعطي النتيجة نفسها.
- انتهاء العملية أو إعادة إرسال complete لا يعيدان الجلسة إلى الحالة النشطة.

## API-002: حذف مشروط بفراغ المجلد بصورة ذرية

**التصنيف:** فجوة في العقد الموثق، لا عطل حي أعيد إنتاجه.

الإضافة تقرأ المجلد للتأكد من فراغه قبل حذفه. يستطيع جهاز آخر إضافة ملف بين GET وDELETE؛ والحذف الحالي ينقل محتويات المجلد إلى السلة، وليس المجلد الفارغ فقط.

### المطلوب

إضافة خيار حذف مشروط ينفذ فحص الفراغ والحذف داخل عملية ذرية واحدة. المثال التالي **اقتراح للعقد، وليس معاملًا حاليًا يعتمد عليه العميل**:

```http
DELETE /api/v1/folders?path=/parent/&name=child&ifEmpty=1
```

- إن أصبح المجلد غير فارغ، أعد `409 FOLDER_NOT_EMPTY` دون أي تغيير.
- افحص الملفات والمجلدات الفرعية والجلسات النشطة ذات الصلة، لا قائمة عرض قد تستبعد عناصر مهمة.
- تجاهل الجلسات النهائية طبقًا لتصحيح API-001.
- احسم ترتيب عملية إنشاء ملف وعملية الحذف؛ لا تسمح بنجاحهما مع فقد الملف الجديد.
- أبقِ الحذف التكراري غير المشروط عملية مختلفة أو خيارًا صريحًا موثقًا.

**اختبار القبول:** نفذ إنشاء ملف وحذفًا مشروطًا بالتوازي مرات متعددة. إن نجح إنشاء الملف أولًا، يجب أن يرفض الحذف؛ لا يكفي فحصان منفصلان خارج transaction أو نقطة تسلسل مكافئة.

## API-003: قفل مزامنة موزع ذري

**التصنيف:** متطلب تزامن؛ لا يوجد عقد lock/lease ذري موثق يعتمد عليه العميل حاليًا.

ملف القفل المخفي الحالي حماية استرشادية. يستطيع جهازان رؤية عدم وجود قفل في اللحظة نفسها ثم إنشاء علامتي قفل؛ هوية جهاز مستقلة لا تجعل الاستحواذ ذريًا.

### المطلوب

- lease واحد لكل حساب ومسار مزامنة مطبع، مع استحواذ ذري.
- ربط lease بمالك فريد ورمز غير قابل للتخمين ومدة صلاحية محددة.
- إرجاع تعارض واضح عند استحواذ جهاز آخر، بدل نجاح الاستحواذين.
- تجديد وإطلاق القفل فقط عند مطابقة رمز المالك الحالي.
- عدم السماح لمالك انتهى قفله بإطلاق قفل استحوذ عليه جهاز آخر.
- توثيق TTL والتجديد وسلوك انقطاع الجهاز؛ واستخدام وقت الخادم.
- لضمان منع كتابات المالك القديم فعلًا، تحقق من lease أو fencing token داخل عمليات الكتابة، لا عند الاستحواذ وحده.
- اشتق هوية الحساب من المصادقة؛ لا تثق في account id يرسله العميل لتوسيع النطاق.

**اختبارات القبول:** استحواذان متزامنان يعطيان فائزًا واحدًا، واستحواذ جديد بعد انتهاء TTL لا يستطيع الرمز القديم تجديده أو إطلاقه أو تنفيذ كتابة محمية به.

## API-004: إظهار الجلسات التي تمنع العملية

**التصنيف:** متطلب تشخيص وإدارة، وليس إثباتًا أن مسارًا غير موثق غير موجود داخليًا.

العقد المتاح يشرح قراءة جلسة عندما يعرف العميل معرّفها، لكنه لا يشرح تعداد الجلسات المخفية التابعة لمجلد. لا يستطيع العميل تحديد جلسة قديمة تمنع الحذف إذا لم يكن هو من أنشأها أو لم يحفظ معرّفها.

### المطلوب

- توثيق تعداد الجلسات المملوكة للحساب، مع تصفية بالمسار والحالة وpagination.
- عرض معرّف الجلسة ونوعها وحالتها وهل هي نشطة فعلًا، ووقت الإنشاء/آخر تقدم والانتهاء.
- عند `UPLOAD_IN_PROGRESS`، إرجاع معرّفات الجلسات النشطة التي تحجب العملية، وفق صلاحيات الحساب، دون محتوى الملفات أو بيانات حسابات أخرى.
- تمييز `ready` و`committed` والحالات الملغاة عن الحالات القابلة للإلغاء.
- تحديد مدة الاحتفاظ بالجلسات المهجورة وطريقة تنظيفها دون حذف محتوى ملتزم أو تاريخ إصدارات.
- توثيق أن رد إلغاء `202 queued` لا يعني انتهاء الإلغاء؛ يجب أن يمكن تأكيده عبر الحالة لاحقًا.
- الحفاظ على `X-Request-Id` و`error.code` و`Retry-After` حيث يلزم في كل مسار فشل.

لا ينبغي إجبار العميل على إلغاء كل جلسات الحساب أو تخمين معرّفاتها لحل مجلد واحد.

## API-005: تحديث محتوى مرتبط بإصدار متوقع

**التصنيف:** مطلب لضمان التزامن الكامل؛ لم نثبت أن الخادم يفتقر داخليًا إلى كل وسائل المقارنة، لكن لا يوجد عقد موثق كافٍ يعتمد عليه العميل لجميع هذه العمليات.

إعادة قراءة metadata قبل التحديث تخفف السباق، لكنها لا تمنع تغير الملف بعد القراءة وقبل PATCH أو فتح revision. كما أن ضمان مصدر الجلسة خلال prepare/complete وحده لا يثبت أن المصدر ما زال هو الإصدار الذي راجعه المستخدم قبل prepare.

### المطلوب

- توثيق رمز إصدار للمحتوى يمكن الحصول عليه من metadata والقوائم، مثل ETag أو version متزايد، مع تعريف واضح لمعناه.
- دعم شرط إصدار ذري عند `PATCH` للمحتوى وعند فتح/إتمام revision، وربطه بالإصدار الذي راجعه العميل.
- مثالان مقترحان، لا معاملات حالية مؤكدة: `If-Match` لـPATCH، أو `expectedVersion` مع `baseId` في طلب revision.
- عند اختلاف الإصدار، أعد `412 PRECONDITION_FAILED` أو `409 VERSION_CONFLICT` دون كتابة فوق الإصدار الجديد.
- لا تجعل قراءة رأس أحدث بعد العملية دليلًا على أن ذلك الرأس هو النسخة التي التزمت بها العملية السابقة.
- أعد في نجاح الكتابة هوية الإصدار الملتزم وبصمته، ولو كانت بقية metadata مختصرة.
- وضح الفرق بين ETag للمحتوى وأي ETag آخر، ودلالة البصمة للملفات متعددة الأجزاء.

**اختبار القبول:** يقرأ A الإصدار V1، ثم يلتزم B بالإصدار V2. محاولة A التحديث المشروط بـV1 ترفض بلا تغيير V2؛ وكذلك إذا تغير المصدر أثناء إعداد أو إنهاء revision.

## ما ليس عيب API مؤكدًا

- رفض `UploadChecksumMismatch` في سجل الملف المحلي لا يكفي وحده لإثبات خطأ الخادم. خطة 14502 بايت كانت صحيحة، واختبار حي ببيانات UTF-8 مولدة وحجم مماثل نجح بعد إرسال ArrayBuffer صحيح.
- وجد خلل في الإضافة عند تمرير Uint8Array إلى `requestUrl`؛ صحح في الإصدار 1.7.11. لا تعالج ذلك بإزالة فحوص الحجم أو البصمة من الخادم.
- فرضية رفض الجزء الأخير لأنه أصغر من min ليست تفسيرًا مثبتًا للملف المتعثر: نهاية خطته الفعلية 1301 بايت، وهي أكبر من min=1024.
- `ALREADY_EXISTS` للأسماء الموجودة في السلة سلوك مذكور في العقد، وليس عيبًا ثبت هنا. أي تغيير لسياسة إعادة استخدام الاسم يحتاج قرارًا وتوثيقًا واضحين، لا حذفًا نهائيًا تلقائيًا.
- لم يثبت خلل عام في المصادقة أو القوائم أو تنزيل الأجزاء ضمن الاختبارات المنفذة.

## تنظيف بيانات التشخيص بعد إصلاح API-001

هذه ثلاثة مجلدات اختبار داخل `/Obsidian/X0/`، لا مجلدات ملاحظات المستخدم. نقلت ملفات اختبارها إلى السلة، لكن حذف المجلدات الفارغة بقي مرفوضًا:

- `.tdrive-diagnostic-ca5f5576-5c16-4d75-962d-b0fb12395b7d`
- `.tdrive-diagnostic-5f465b6c-346d-47c7-805d-52477138e171`
- `.tdrive-diagnostic-b5dae834-e466-4032-8185-7eaaff9a2e8e`

بعد التصحيح يمكن إعادة أمر التنظيف لكل اسم معروف:

```text
node scripts/check-sync-live.js --cleanup <diagnostic-folder-name>
```

لا تمسح سلة الحساب كاملة، ولا تلغِ جلسات أجهزة أخرى، ولا تحذف تاريخ الإصدارات لإزالة العائق.
